# P0.7 — Cross-Workspace IDOR, Tenant Routing, Cache & Media Access

- Date: 2026-11-13
- Status: BRIEF COMPLETE — implementation and security verification pending
- Plan revision: 2.7
- Scope: API authorization boundaries, Workspace-to-Tenant database resolution, cache policy, media filesystem isolation, disposable tests only

## 1. Objective

Prove that a user, request, database connection, cache entry, or media object scoped to one Workspace cannot be used to read or mutate another Workspace. POS and ONLINE must remain isolated by Workspace identity and their independently provisioned Tenant databases.

No persistent Control/Tenant database changes, Workspace reclassification, production data mutation, commit, push, or deployment are included.

## 2. Initial architecture observations

These are review findings to validate and address with tests; they are not yet claims of confirmed exploitable vulnerabilities.

1. `WorkspaceDatabaseRegistry.forMembership()` checks active membership and resolves the Workspace's database record on each call, then caches a PrismaClient by `workspaceId`. When a cached client exists, the method returns it without comparing its connection identity to the currently resolved database record. A database remap or credential rotation may therefore leave a stale client attached to the old endpoint until explicitly evicted.
2. `WorkspaceModuleCapabilityGuard` correctly requires a route-scoped `params.workspaceId` and rejects conflicting `x-workspace-id` values for guarded Commerce routes. `RbacGuard` independently falls back to the header when the route parameter is absent. All current Commerce controllers are module-guarded, but Workspace, Module and future controllers need a complete route-by-route IDOR review.
3. No Nest cache module, CacheInterceptor, cache-manager or Redis cache use was found in the initial API source scan. The review must still check browser/CDN response policy and any non-Nest cache implementation before concluding there is no server cache risk.
4. Media records and object keys are stored in the Tenant database and generated with a Workspace ID prefix. Authenticated media reads resolve the database through `forMembership()`. Both MediaService and ImageImportService use lexical `path.resolve` containment checks; symlink-aware containment and explicit Workspace-prefix validation need verification.
5. Media GET currently emits `Cache-Control: private, max-age=300`. Confirm this is safe for the authenticated media threat model and prevent shared proxy/CDN caching.

## 3. Work packages

### P0.7-A — Cross-Workspace IDOR
- Inventory every route that accepts a Workspace ID, membership ID, module ID, tenant resource ID or media identifier.
- Verify membership and ACTIVE Workspace checks are enforced server-side, including list/detail/mutation routes.
- Verify nested resource IDs are queried inside the selected Workspace Tenant DB and cannot resolve against another Workspace.
- Verify route Workspace ID is authoritative; conflicting, repeated or malformed `x-workspace-id` values fail closed.
- Verify membership and role operations cannot use a membership ID belonging to a different Workspace.
- Verify ONLINE cannot reach POS-only Commerce controllers through alternate routes.

### P0.7-B — Tenant routing and connection lifecycle
- Test that two Workspace IDs resolve to distinct database identities and Prisma clients.
- Test concurrent requests for two Workspaces do not cross-route.
- Test absent membership, suspended Workspace, missing database mapping, invalid database identity and missing encrypted credential fail closed.
- Test database mapping/credential changes cannot continue using a cached client for the old identity.
- Test eviction, disconnect and concurrent first-use behavior without leaking or duplicating clients.
- Never print database URLs, passwords, decrypted credentials or environment secrets.

### P0.7-C — Cache and HTTP response isolation
- Complete repository-wide scan for in-memory, process, browser, CDN and proxy caches.
- If application cache exists, require Workspace/Tenant identity in keys and scoped invalidation.
- If no server cache exists, document that result and verify private/no-store policy for sensitive authenticated endpoints, especially media.
- Verify no public cache policy can store authenticated Tenant responses.

### P0.7-D — Media and staging isolation
- Verify media metadata lookup occurs only in the caller's Tenant DB.
- Verify media and staging keys are Workspace-prefixed and cannot escape the configured root.
- Test traversal, Windows separators, absolute paths, encoded traversal, symlink/path confusion and cross-Workspace keys.
- Verify a media ID from Workspace A returns no data in Workspace B, including ORIGINAL, MAIN and THUMBNAIL.
- Verify image-import batch IDs are scoped to the current Tenant DB and uploader; preview/commit cannot cross Workspace boundaries.
- Verify deleted/missing media cannot be served and authenticated media responses cannot be shared-cacheable.

## 4. Acceptance criteria

- [ ] User without active membership cannot access any Workspace-scoped route.
- [ ] User in Workspace A cannot read or mutate Workspace B resources by swapping path IDs, nested IDs, membership IDs, media IDs or batch IDs.
- [ ] Conflicting/multi-value Workspace headers are rejected; header alone never establishes tenant scope.
- [ ] POS and ONLINE requests resolve to their own configured Tenant database under parallel execution.
- [ ] Missing, invalid, remapped or stale database identity fails closed; stale clients are disconnected/replaced safely.
- [ ] Concurrent client initialization is single-flight per Workspace and does not cross-contaminate identities.
- [ ] Cache scan is documented; any discovered cache is Workspace-scoped, and authenticated media is not shared-cacheable.
- [ ] Media/staging filesystem paths remain inside the storage root and expected Workspace prefix, including symlink/path edge cases.
- [ ] Cross-Workspace media and image-import identifiers cannot disclose or mutate data.
- [ ] Automated unit tests and localhost-only disposable Control/Tenant integration tests pass.
- [ ] API typecheck/build and `git diff --check` pass.
- [ ] No persistent Control/Tenant DB changes, no real sale/order, no production activation, no commit/push/deploy.

## 5. Planned verification

- Add focused unit tests for WorkspaceDatabaseRegistry identity comparison, stale-client eviction, concurrent initialization and fail-closed cases.
- Add filesystem tests using a temporary directory for traversal and symlink behavior.
- Add localhost-only disposable database integration tests with two synthetic Workspace identities and isolated Tenant databases. Require explicit `TEST_POSTGRES_ADMIN_URL` guard, unique database names, and guaranteed cleanup in `finally`.
- Extend HTTP/RBAC integration tests for route/header mismatch and cross-Workspace resource IDs where the existing harness supports it.
- Run existing P0.5/P0.6 guard and RBAC regression suites.
- Do not point destructive test helpers at `pos-local`, `e2e-commerce-20261106`, or any persistent database.

## 6. Out of scope

- Applying Control Plane or Tenant migrations.
- Reclassifying or provisioning existing Workspaces.
- Enabling/disabling persistent Modules or changing persistent RBAC rows.
- Introducing Redis or a new distributed cache without a demonstrated requirement.
- Migrating local media storage to S3/shared storage.
- Public media URLs or public Store publishing.
- Commit, push, deployment or production activation.

## 7. Implementation order

1. Complete route/tenant/media/cache inventory and add focused regression tests.
2. Fix confirmed authorization and database-client lifecycle weaknesses.
3. Harden media filesystem containment and authenticated response cache headers.
4. Run unit, disposable integration, typecheck/build and diff checks.
5. Publish implementation report and update `plan.md` only after evidence supports the acceptance claims.
