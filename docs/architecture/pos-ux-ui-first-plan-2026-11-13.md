# POS UX/UI-first implementation plan\n\nDate: 2026-11-13\nStatus: Priority change — cashier-facing POS before further backend expansion.\n\n## Decision\n\nPrioritize the in-store POS experience now. The existing Sales Orders services and `/workspace/[slug]/orders` page are a working foundation, but the page is an order-management/order-entry surface rather than a fast cashier checkout. Keep Orders as the back-office record, and build a dedicated cashier route at `/workspace/[slug]/pos`.\n\nPause Online Store checkout, CRM, advanced reporting, payment-provider integrations and non-essential backend features until the core POS UX has been reviewed and delivered. This is a development priority, not a production-readiness declaration.\n\n## Current foundation\n\n- Server-side Order creation resolves Store listing, sellable UOM, price, tax and stock, then reserves inventory.\n- RESERVED Orders can be posted (consume reservation, create SALE movement and WAC cost snapshot) or cancelled.\n- Payment ledger supports CASH, CARD, BANK_TRANSFER and OTHER; Returns and Refund ledger exist.\n- Idempotency, audit, API Auth/RBAC and disposable-workspace HTTP E2E are implemented.\n- Current payment ledger is manual/internal only: no card charge, bank/QR verification, provider webhook or actual money movement.\n- `pos-local` currently lacks sellable Store listings, prices, Tax Profile/Tax Rates and opening stock; its alcohol products are DRAFT placeholders.\n\n## UX principles\n\n1. Cashier-first: one primary task, few steps, obvious next action.\n2. Touch-first: large controls and readable totals for desktop POS/tablet.\n3. Fast item entry: persistent search, SKU/barcode support, keyboard focus and shortcuts.\n4. Clear cart: item/variant/UOM, quantity, unit price, line total and remove/edit actions.\n5. Transparent totals: subtotal, tax and grand total; server remains authoritative.\n6. Explicit payment state: amount due, tender, received amount, change, remaining balance and manual-verification disclaimer.\n7. Designed failure states: loading, empty, no result, out of stock, stale price/tax, permission denied, network failure, duplicate submit and retry.\n8. Accessible, responsive and consistent with the existing clean SyncUp workspace style.\n\n## Delivery milestones\n\n### POS-0 — Workflow specification\n- Map: enter POS → confirm Store/Branch/Warehouse → search item → cart → review → create/reserve → post sale → record payment → receipt.\n- Define Cashier/Manager/Owner permissions, defaults and denied states.\n- Specify empty/loading/error/retry/partial-payment states and screen map.\n- No live database writes.\n\n### POS-1 — Dedicated POS shell\n- Add `/workspace/[slug]/pos` and Workspace navigation.\n- Header shows store/branch/warehouse and cashier context.\n- Desktop: product discovery on the left, persistent cart/checkout panel on the right.\n- Tablet: responsive stacked or drawer layout with cart always easy to reach.\n- Build reusable product tile, search, quantity stepper, totals, payment and confirmation components.\n- Use fixture data initially; do not depend on production catalog completeness.\n\n### POS-2 — Product discovery and cart\n- Search by product name, SKU and barcode where supported.\n- Show only sellable Store listings/variants; explain unavailable items.\n- Add/edit quantity/UOM/remove lines, clear cart with confirmation.\n- Show server-resolved price/tax/availability; never invent client-authoritative totals.\n- Prevent duplicate item actions and double-submit.\n- A browser-only parked cart must be labelled temporary. Do not present it as a durable suspended bill until a backend lifecycle exists.\n\n### POS-3 — Checkout and payment\n- Display API-confirmed order lines, tax and amount due.\n- Respect current state sequence: create/reserve → post sale → record payment.\n- Cash entry calculates change from the confirmed total.\n- Bank transfer/QR/Card remain manual ledger entries with clear confirmation wording until provider verification exists.\n- Support split/partial tender within API limits.\n- If posting succeeds but payment recording fails, keep the Order reference and offer safe payment retry; never create a second Order.\n\n### POS-4 — Receipt\n- Printable receipt based on persisted Order/Payment data: store, order number, time, items, quantities, tax, totals, tenders and change.\n- Add print CSS for standard and thermal widths.\n- Reprint audit must be supported before describing reprint as audited.\n- Do not claim tax-invoice/legal compliance until requirements and setup are verified.\n\n### POS-5 — Sale lookup and exceptions\n- Show recent sales and payment/posting states in POS.\n- Link cancel/return/refund to existing permission-gated Orders management.\n- Provide safe recovery for interrupted requests and stale data.\n\n### POS-6 — Test and handoff\n- Component tests and Playwright desktop/tablet/keyboard cashier journey.\n- Real API/Auth/RBAC tests in disposable workspace; keep stubbed UI tests labelled separately.\n- Regress existing Orders, Product Catalog, reservations and stock posting.\n- No test fixtures or invented data in registered production-like workspaces.\n\n## Dependencies before full operational rollout\n\n| Capability | Status / decision |\n|---|---|\n| Cashier shift, opening float, closing count | Not implemented; design UX now, implement before controlled live cashier operation |\n| Durable suspended bills | Not implemented; requires backend lifecycle |\n| Cash drawer reconciliation and variance | Not implemented; rollout gate |\n| Receipt sequence and audited reprint | Not complete; verify requirements and add audit support |\n| Payment provider / QR verification | Not implemented; manual ledger only |\n| Real catalog, Store listings, prices, tax and opening stock | Missing in pos-local; requires actual data and separate approval |\n| Encrypted off-host backup and restore | Outstanding production-readiness blocker |\n\n## Definition of Done\n\n- Cashier completes a sale from the dedicated POS screen without using the back-office Order form.\n- Product discovery, cart, checkout, payment result and receipt are clear on desktop/tablet.\n- Prices, tax, stock and payment states come from server responses.\n- Retry/double-submit behavior is safe and tested.\n- API RBAC remains authoritative and the existing Orders management regression suite passes.\n- Missing shifts, cash reconciliation, durable parked bills, legal receipt and payment-provider capabilities remain explicit rollout gates.\n\n## Immediate next step\n\nStart with POS-0 and POS-1: inspect existing Workspace layout/components, settle the cashier screen structure, then implement the dedicated POS shell with fixture data. Do not start Shift APIs, provider integration or Online Store checkout first.\n
