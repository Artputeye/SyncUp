# P0.5 — API Guard: Workspace Type & Module Capability

- Track: 0 — Platform Separation Foundation
- Status: BRIEF READY — source implementation follows this brief
- Date: 2026-11-13
- Depends on: P0.1 Workspace Type Registry, P0.2 Module Compatibility, P0.3 persisted Profile identity/version, P0.4 type-aware landing

## Objective

Enforce Workspace product boundaries at the API boundary. A valid login alone is insufficient: business endpoints must prove active membership, ACTIVE Workspace status, supported Workspace Type, a persisted Profile matching that Type and Version, and an enabled Module capability before reaching tenant business services.

## Audit Findings

1. Existing business controllers use `AuthGuard` and `RbacGuard`; most declare individual `@RequirePermission` metadata.
2. `RbacGuard` currently resolves Workspace ID from route params or `x-workspace-id`, checks permission through `RbacService`, and sets `request.workspaceId`. It does not evaluate Workspace Type, Profile identity/version, or enabled Module state.
3. `RbacService.hasPermission` verifies an ACTIVE Workspace membership, and Owner bypasses individual permission keys; neither behavior proves product/module capability.
4. `WorkspaceDatabaseRegistry.forMembership` verifies ACTIVE membership and resolves the server-side Tenant DB, but does not verify Type/Profile or Module enablement.
5. Current POS commerce controllers (tenant, product/media/import, inventory, sales/orders) are guarded for authentication/RBAC but have no shared Module Capability guard.
6. `ModulesController` is a platform management surface. Its service checks active membership and `modules.manage`; install/enable already run compatibility checks, while disable must remain available as a recovery action.
7. Legacy Workspaces with NULL Type/Profile and POS/ONLINE type mismatch must fail closed for commerce APIs. UI hiding is not an authorization boundary.

## Design

- Add a dedicated, reusable Workspace Module Capability decorator and guard in Core Modules.
- Resolve Workspace ID from the route parameter for current tenant routes; do not let a conflicting client header override a route-scoped ID.
- Guard evaluation order:
  1. authenticated user exists;
  2. route Workspace ID exists;
  3. user has active Membership and Workspace is ACTIVE;
  4. registered Module exists and its manifest allows the Workspace Type;
  5. persisted Profile ID + Version resolves exactly for the Workspace Type and allows the Module;
  6. the ModuleInstallation row is both `enabled=true` and `status=ENABLED`.
- Fail closed with HTTP 403 for missing membership, inactive Workspace, NULL/unsupported Type, stale/missing Profile, incompatible Type/Profile, or disabled/missing Module. Do not reveal Tenant database credentials or internal registry data.
- Attach the guard to all existing business controllers that are part of the POS Commerce Module: store/branch/warehouse/settings, product/media/image import, inventory/opening stock, and sales/orders/returns/payments.
- Keep the existing per-action RBAC permission checks. Module capability is an additional gate, not a replacement.
- Keep Module management endpoints outside the business capability guard so operators can inspect compatibility, install/enable compatible modules, and disable a module during recovery.
- Keep Workspace Database resolution server-side through `WorkspaceDatabaseRegistry`; no client-supplied database/tenant connection information.

## Compatibility / Rollout Impact

- Existing Workspaces whose persistent Control DB migration/backfill has not been approved/applied will remain untyped and therefore cannot access guarded commerce APIs after this code is deployed.
- A Workspace must have a valid persisted Type/Profile and an ENABLED ModuleInstallation before business routes are available.
- This source milestone must not mutate persistent Control/Tenant DBs or automatically install/enable modules. A separate, explicitly approved migration/activation step is required before deploying to an existing environment.
- The guard does not replace resource-level Store/Branch/warehouse ownership checks or the separate P0.7 IDOR/cache/media security assessment.

## Acceptance Criteria

| ID | Acceptance |
|---|---|
| P0.5-A | A dedicated module-capability guard exists and resolves the route Workspace ID without trusting a conflicting header. |
| P0.5-B | Guard denies unauthenticated/missing-context, non-member, inactive Workspace, and untyped Workspace requests. |
| P0.5-C | Guard denies Workspace Type mismatch, missing/stale Profile ID/version, and Profile that does not allow the requested Module. |
| P0.5-D | Guard denies missing, disabled, or non-ENABLED ModuleInstallation. |
| P0.5-E | All current POS Commerce business controllers apply the capability guard in addition to existing RBAC permissions. |
| P0.5-F | Module management endpoints remain reachable to authorized workspace managers for compatibility inspection and recovery/disable operations. |
| P0.5-G | Automated tests cover allow and deny cases, including Owner membership not bypassing Module capability and a conflicting `x-workspace-id` header. |
| P0.5-H | API Prisma validation/generation, typecheck, build, relevant integration tests, and `git diff --check` pass. |
| P0.5-I | No persistent Control/Tenant DB migration, backfill, module installation/enablement, provisioning, deployment, commit, or push occurs. |

## Out of Scope

- Workspace Type/Profile migration or backfill on persistent databases.
- Default Roles/Permission Catalog and navigation composition (P0.6).
- Cross-workspace resource IDOR, cache, file/media penetration testing (P0.7).
- Store/Branch-specific resource scoping changes unless required to close a direct capability bypass.
- Production activation or module installation on existing Workspaces.
