# P0.3 — Workspace Registry Profile Persistence & Lifecycle Metadata

- Track: 0 — Platform Separation Foundation
- Status: IN PROGRESS
- Date: 2026-11-13
- Source of truth: `plan.md`

## Objective

Persist the selected Provisioning Profile ID/version on each newly created typed Workspace and record its provisioning lifecycle in the Control Plane. Runtime module compatibility must use the persisted profile snapshot rather than silently deriving a different profile from Workspace Type.

## Inspection Findings

- `Workspace` currently stores nullable `type`, status and timestamps only.
- P0.2 profiles are code-backed: `pos-standard@1.0.0` and `online-standard@1.0.0`.
- Workspace creation currently stores Type then provisions the Tenant DB; the provisioning service marks status ACTIVE/FAILED.
- Module compatibility currently derives a profile from Workspace Type, so it cannot detect persisted profile drift.
- Existing legacy Workspaces may have NULL Type and must remain untouched.

## Scope

1. Add nullable Workspace Registry fields:
   - `provisioning_profile_id`
   - `provisioning_profile_version`
   - `provisioning_started_at`
   - `provisioned_at`
   - `provisioning_error`
2. Assign the matching Profile ID/version atomically when creating a new typed Workspace.
3. Require profile ID/version and validate their compatibility with Workspace Type before provisioning begins.
4. Record start, successful completion and failure details without storing secrets or credentials in error metadata.
5. Return persisted Profile and lifecycle fields from Workspace list/create API responses.
6. Resolve module compatibility using the persisted profile ID/version; fail closed for missing, unknown, stale or Type-mismatched profiles.
7. Preserve NULL profile/lifecycle fields for existing legacy Workspaces; no automatic backfill.
8. Add a localhost-only disposable Control DB migration rehearsal covering P0.1 + P0.3, sentinel preservation, typed inserts and lifecycle updates.
9. Extend module lifecycle integration coverage for persisted profiles.

## Design Decisions

- Profile registry remains code-backed and immutable in P0.3; P0.3 persists the selected identity/version, not editable profile definitions.
- New POS Workspaces receive `pos-standard@1.0.0`; new ONLINE Workspaces receive `online-standard@1.0.0`.
- Existing Workspaces are not backfilled, even if their Type is already POS/ONLINE.
- Lifecycle timestamps are nullable and describe the most recent provisioning attempt. A failed attempt sets `provisioning_error`; success clears it.
- The provisioning error is truncated, sanitized and never includes database URLs, usernames, passwords or encrypted credentials.
- No automatic retry, conversion, profile upgrade or profile re-selection is included.
- No Tenant DB schema changes are required.
