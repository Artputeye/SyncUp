# P0.4 — Workspace Selector & Type-aware Landing

- Track: 0 — Platform Separation Foundation
- Status: BRIEF APPROVED FOR SOURCE IMPLEMENTATION
- Date: 2026-11-13
- Depends on: P0.1 Workspace Type Registry, P0.2 Provisioning Profile Compatibility, P0.3 Persisted Profile/Lifecycle Metadata

## Objective

Make POS and ONLINE workspaces visibly distinct at selection and entry points. The selector must show the persisted Workspace Type and Provisioning Profile identity/version, and opening a workspace must lead to a type-appropriate landing experience without presenting POS-only navigation in an ONLINE workspace.

## Scope

1. Extend the selector's Workspace view model to consume API-provided `type`, `provisioningProfileId`, `provisioningProfileVersion`, and lifecycle metadata where present.
2. Present a clear product identity for POS and ONLINE, profile ID/version, owner/member role, and provisioning/active/error status. Legacy rows with NULL Type/Profile must be clearly marked as unclassified and must not be silently labelled POS or ONLINE.
3. Keep selection membership-driven: only render workspaces returned by the authenticated `GET /api/workspaces` response. Do not trust a client-supplied Workspace ID as authorization.
4. Route POS workspace root to the existing POS landing (/pos); route ONLINE workspace root to a dedicated ONLINE landing state. ONLINE currently has no eligible modules, so the page must explain that the workspace is ready for Online modules without showing POS checkout/catalog controls.
5. Provide consistent Workspace switching back to the selector from both landing experiences.
6. Ensure POS navigation/actions are not exposed in ONLINE landing. Do not claim frontend hiding is an authorization boundary.
7. Add focused Playwright coverage for selector metadata, POS/ONLINE routing and switching, and legacy unclassified handling using mocked API responses.

## Out of Scope

- Persistent Control/Tenant DB migrations, backfills, provisioning or mutation.
- API authorization redesign or Workspace Type API guards (P0.5).
- Type-specific navigation registry, default roles or permission catalog (P0.6).
- Cross-workspace IDOR, tenant routing, cache and media penetration testing (P0.7).
- Online commerce domain modules or checkout.
- Commit, push, deployment, or real production activation.

## Acceptance Criteria

## Implementation Notes

- Keep Profile identity sourced from the existing Workspace API response; do not hardcode a profile from Type alone.
- Use the existing POS route and POS shell. ONLINE landing is intentionally an informative shell until Online modules are delivered.
- UI routing is navigation behavior only. Server-side authorization remains authoritative and is not weakened or replaced.
