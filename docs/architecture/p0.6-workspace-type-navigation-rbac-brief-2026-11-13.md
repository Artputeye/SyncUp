# P0.6 — Workspace-type Navigation, Default Roles & Permission Catalog

- Track: 0 — Platform Separation Foundation
- Status: IMPLEMENTED — see p0.6-workspace-type-navigation-rbac-implementation-2026-11-13.md
- Date: 2026-11-13
- Depends on: P0.1 Workspace Type Registry, P0.2 Provisioning Profile & Module Compatibility, P0.3 Profile Persistence, P0.4 Type-aware Landing, P0.5 API Workspace/Module Guard

## 1. Objective

Make POS and ONLINE Workspaces present and authorize only the navigation entries, default roles, and permissions that belong to their persisted Workspace Type and enabled Module capabilities. Keep Workspace membership and role assignments isolated per Workspace. The backend remains authoritative; hiding a menu item is not an authorization boundary.

## 2. Current-state findings

1. `apps/api/src/core/rbac/permission-catalog.ts` defines one global `WORKSPACE_PERMISSIONS` list and one `DEFAULT_WORKSPACE_ROLES` matrix. Commerce permissions are mixed with platform/workspace-level permissions; the definitions do not declare Workspace Type or owning Module.
2. `Permission.key` is globally unique in Control DB. `Role` is Workspace-scoped by `workspaceId + key`; `MembershipRole` attaches a role to a membership. This supports separate role assignments per Workspace, but the catalog and default matrix are not type-aware.
3. `WorkspacesService.ensureDefaultRoles()` currently seeds every permission and default role set. It is called at Workspace creation, from `listRoles()` (a GET/read path), and before member assignment. The GET side effect can create permissions/roles/role-permission links and can add missing defaults after a user merely opens the role page.
4. `WorkspacesService.updateRolePermissions()` currently accepts any globally-known permission key. It does not verify that each permission belongs to the target Workspace Type or to a module allowed by its persisted Profile.
5. `apps/web/src/app/workspace/[slug]/page.tsx` hardcodes POS links (Modules, Store, POS, Orders, Inventory, Products) in the generic Workspace shell. Typed ACTIVE Workspaces redirect to POS or Online landing pages, and the Online landing is a placeholder without a shared navigation catalog.
6. `COMMERCE_MODULE_MANIFEST` declares Commerce as POS-only and lists its permission keys. The persisted provisioning profile is the source of allowed/default modules. P0.5 already enforces Type/Profile/Module capability on protected API controllers.

## 3. Target design

### 3.1 Permission catalog

- Replace the unqualified permission array with a typed catalog definition. Each permission has a stable globally unique `key`, description, scope/owner, supported Workspace Types, and optional `moduleId`.
- Keep platform administration permissions outside Workspace RBAC; `User.isPlatformAdmin` and `PlatformAdminGuard` remain authoritative for platform-admin operations.
- Core Workspace permissions (for example `workspace.view`, `members.view`, `members.manage`, `roles.manage`, `modules.manage`) are explicitly marked as Core permissions and declare which Workspace Types they support.
- Commerce permissions are owned by `commerce`, support POS only, and must be included in the resolved Profile's `allowedModuleIds` before they can be seeded, assigned, or displayed.
- Future Online module permissions are not invented as active capabilities in this milestone. Add them only when an Online module manifest/profile defines them.
- Preserve existing permission keys for compatibility; do not rename keys or silently widen their scope.

### 3.2 Type-aware default role matrix

- Resolve the Workspace's persisted Type + exact Profile ID/version before seeding. Missing, stale, unsupported, or mismatched Type/Profile fails closed.
- Define a role matrix per Workspace Type. POS retains appropriate operational roles (Admin, Manager, Cashier, Inventory Staff on-demand, Member, Viewer) with only Core + POS/Commerce permissions. ONLINE receives only Core permissions and a deliberately minimal baseline role set until Online modules exist; it receives no Commerce role grants.
- Admin's role grants are limited to the permissions available to that Workspace Type/Profile. Workspace Owner's existing owner bypass remains Workspace-scoped; it does not bypass P0.5 module capability checks.
- Role creation and default permission seeding happen only through explicit bootstrap/assignment paths, never through list/read endpoints.
- Existing custom role permissions must not be overwritten by default seeding. Default seed is additive and idempotent. A future explicit reconciliation process must be separately designed and approved.

### 3.3 Permission enforcement and API contracts

- Add a single resolver for permissions available to a Workspace from persisted Type/Profile and currently registered compatible modules.
- `listRoles` is read-only and returns only permissions available to that Workspace. It must not create Permission, Role, or RolePermission rows.
- `updateRolePermissions` rejects keys that are unknown, unsupported by Workspace Type, absent from the Profile, or owned by a module that is not enabled for that Workspace. Validate the full request before changing any links; failed requests leave the role unchanged.
- Member role assignment accepts only role definitions valid for that Workspace Type. Cross-type role keys must be rejected even if a row exists from legacy/manual data.
- Keep P0.5 `WorkspaceModuleCapabilityGuard` and per-action RBAC as separate checks. Navigation visibility is not a substitute for either.

### 3.4 Navigation catalog and rendering

- Define a typed navigation catalog in Core/UI composition with stable item IDs, label, route, icon identifier, supported Workspace Types, optional owning Module, and required permission keys.
- Core navigation items (Workspace switcher, profile/account actions, member/role administration where supported) are not tied to Commerce.
- Commerce navigation items (Store, Products, Inventory, Orders, POS) are POS-only and require the Commerce module to be enabled plus the appropriate permission(s).
- Compose navigation from the authenticated Workspace's persisted Type/Profile, enabled Module installations, and effective permissions. Do not infer type from slug, route, or client-supplied headers.
- POS and Online shells use the same composition contract but may render different product-specific layouts. ONLINE must never render POS/Commerce links.
- Unknown catalog items, stale profiles, missing module installations, or missing required permissions are hidden in the UI and remain denied by backend authorization.
- Preserve the current Workspace switch/logout affordances in both shells.

### 3.5 Safe initialization and legacy compatibility

- Remove `ensureDefaultRoles()` from GET/list code paths. Role list endpoints must be side-effect-free.
- New Workspace bootstrap seeds only the resolved Type/Profile matrix before provisioning can mark the Workspace ACTIVE.
- Adding a member may ensure the requested valid role exists, but must not seed unrelated type-incompatible roles or permissions.
- Existing legacy Workspaces with NULL Type/Profile remain unclassified and do not receive an inferred POS/ONLINE role matrix. Do not backfill or mutate persistent Workspaces in P0.6.
- No persistent Control DB migration, backfill, role reseed, or permission rewrite is included in this milestone.

## 4. Implementation sequence

1. Add pure catalog/resolver unit tests for permission ownership, Workspace Type, Profile module allow-list, and role matrices.
2. Refactor permission catalog into Core + module-owned typed definitions while preserving stable keys.
3. Refactor Workspace role bootstrap to resolve Type/Profile and seed only the eligible role/permission set; make listRoles read-only.
4. Validate role assignment and permission edits against the target Workspace's available permission set, with all validation completed before writes.
5. Add a shared navigation composition contract and server/API response scoped to the authenticated Workspace membership.
6. Replace hardcoded POS navigation links with catalog-driven rendering; use POS and ONLINE shells with explicit type separation.
7. Add unit, wiring, disposable Control DB, API authorization, and browser tests; update plan and implementation report.

## 5. Acceptance criteria

### Catalog & roles
- [x] Every permission definition has a stable key, description, scope/owner, supported Workspace Type(s), and module ownership where applicable.
- [x] Commerce permissions are POS-only and unavailable unless the persisted POS Profile allows Commerce.
- [x] POS default roles retain the intended POS operations without granting platform-admin privileges.
- [x] ONLINE default roles contain Core permissions only; no `commerce.*` permission is seeded or assignable.
- [x] Role seeding is idempotent and additive; it does not overwrite customized role permissions.
- [x] Invalid/stale/mismatched Type/Profile fails closed.

### Read/write behavior & authorization
- [x] `GET /workspaces/:workspaceId/roles` performs no Permission, Role, or RolePermission writes.
- [x] Permission edit rejects unknown, cross-type, profile-disallowed, and disabled-module permissions before any DB mutation.
- [x] Member add/change rejects role keys that are not defined for the target Workspace Type.
- [x] Existing Owner semantics remain Workspace-scoped and do not bypass P0.5 module capability guard.
- [x] Backend checks remain authoritative even when a navigation item is hidden or manually requested by URL.

### Navigation & UX
- [x] POS navigation shows only Core items and enabled POS/Commerce items allowed by the user's effective permissions.
- [x] ONLINE navigation contains no POS/Commerce routes or labels.
- [x] Navigation is derived from authenticated membership + persisted Workspace Type/Profile + enabled modules + effective permissions.
- [x] Both shells retain Workspace switching and logout behavior.
- [x] Legacy/unclassified Workspace does not receive a guessed product navigation.

### Verification & safety
- [x] Catalog/role resolver unit tests cover POS, ONLINE, missing/stale Profile, unsupported module, and disabled module.
- [x] API tests cover cross-type role assignment and permission escalation attempts, including Owner behavior.
- [x] Disposable Control DB test proves POS and ONLINE role/permission rows are isolated by Workspace and GET roles is read-only.
- [x] Web typecheck/build and relevant Playwright tests pass.
- [x] `git diff --check` passes.
- [x] No persistent Control/Tenant DB migration, backfill, role seeding, or mutation; no commit, push, or deployment.

## 6. Explicit non-goals

- No Online commerce module implementation or Online business permission invention.
- No migration/backfill/reclassification of existing persistent Workspaces.
- No changes to Tenant DB schemas or business data.
- No replacement of P0.5 backend capability guard.
- No platform-admin RBAC redesign.
- No cross-Workspace data synchronization.

## 7. Risks / decisions to preserve

- Permission keys are globally unique today. Keep that property and add metadata; do not create duplicate keys per Workspace Type.
- Existing Role rows may contain permissions that become invalid under the new resolver. Runtime reads/edits must filter or reject them safely; do not mass-delete legacy grants in this milestone.
- Existing custom role grants must not be lost by additive seeding.
- The current UI has hardcoded routes in the generic Workspace page. Navigation extraction must not accidentally reintroduce the old shared POS menu into Online.
- The Online Profile currently allows no modules. Online should therefore expose only Core navigation until an Online module is registered and approved by its profile.
