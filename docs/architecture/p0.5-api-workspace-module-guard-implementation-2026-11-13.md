## Implemented

1. Added `RequireModuleCapability` metadata decorator and `WorkspaceModuleCapabilityGuard` in Core Modules.
2. The guard requires an authenticated user and a route-scoped `workspaceId`; current business routes no longer rely on `x-workspace-id` as the source of scope. A conflicting or multi-value header is rejected.
3. The guard validates active Membership and ACTIVE Workspace from the Control Plane.
4. It checks that the registered Module manifest allows the persisted Workspace Type.
5. It resolves the exact persisted Provisioning Profile ID + Version against the Workspace Type and checks that the Profile grants the requested Module.
6. It requires a matching ModuleInstallation with both `enabled=true` and `status=ENABLED`.
7. Applied `@RequireModuleCapability("commerce")` and the shared guard to all existing POS Commerce business controllers:
   - tenant settings, stores, branches and warehouses
   - products, product media and bulk image import
   - inventory, stock movements and opening stock
   - sales orders, returns, payments and refunds
8. Existing per-action RBAC permissions remain in place after the capability guard. Owner membership does not bypass Type/Profile/Module capability.
9. Module management endpoints remain outside the business capability guard so authorized managers can inspect compatibility, install/enable compatible modules and disable modules for recovery.
