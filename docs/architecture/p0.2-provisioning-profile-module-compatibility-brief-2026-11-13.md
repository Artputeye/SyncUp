# P0.2 — Provisioning Profile & Module Compatibility

- Track: 0 — Platform Separation Foundation
- Status: IN PROGRESS
- Started: 2026-11-13
- Source of truth: `plan.md`

## Objective

Define versioned, type-specific Provisioning Profiles in the Control Plane module registry and enforce the profile's module allowlist in all module install/enable operations. A POS Workspace must not install an Online-only module, and an ONLINE Workspace must not install a POS-only module. Untyped legacy Workspaces must fail closed for module management.

## Inspection Findings

- Control Plane already has a `ModuleInstallation` table and a module lifecycle service.
- `ModuleManifest` currently declares platform version, dependencies, migrations and permissions, but not compatible Workspace Types.
- `ModuleActivationService` validates platform version, permissions, dependencies and Tenant migrations; it does not check Workspace Type.
- The only currently registered module is `commerce`, whose current scope is Store/Branch/Warehouse/Product/Inventory/Sales and is POS-oriented.
- Existing `pos-local` and older Workspaces may have `type = NULL`; P0.1 intentionally did not classify them.
- The current module lifecycle disposable integration script creates a legacy untyped Workspace and must be updated to apply the P0.1 candidate migration and type its fixture explicitly.

## Scope

1. Add explicit Workspace Type compatibility metadata to module manifests.
2. Define immutable-in-code, versioned Provisioning Profiles for POS and ONLINE.
3. Define an explicit module allowlist per profile. Initially, `commerce` is POS-only; ONLINE has no eligible module until Online domain modules are implemented.
4. Expose the effective profile through a read-only module API endpoint.
5. Enforce Workspace Type and profile allowlist server-side on compatibility, install and enable.
6. Preserve disable as an escape hatch so a previously installed incompatible module can be disabled.
7. Fail closed for untyped legacy Workspaces without guessing their type.
8. Add disposable integration coverage for POS allow, ONLINE deny, untyped deny, and existing lifecycle behavior.
9. Update plan and implementation report.

## Out of Scope

- Persisting Profile ID/Version to Workspace Registry (P0.3).
- Automatically installing default modules during provisioning (future provisioning workflow).
- Creating Online domain modules or splitting the current Commerce domain into smaller POS/Online modules.
- Applying any persistent Control/Tenant DB migration or changing existing Workspace types.
- Creating persistent Workspaces, modifying business data, deployment, commit or push.

## Design Decisions

- Profile registry is code-backed in this milestone; P0.3 will persist the selected profile/version in Control Plane.
- Profile IDs: `pos-standard` and `online-standard`; initial profile version: `1.0.0`.
- `commerce` declares `workspaceTypes: ["POS"]` and is allowed only by `pos-standard`.
- `online-standard` currently allows no module. This is deliberate fail-closed behavior, not a claim that Online is complete.
- Module disable remains allowed even if current profile would reject that module, to permit safe cleanup.
- Existing null-type Workspaces are not migrated or backfilled; module management returns a clear conflict until a separately approved classification/migration.
- Profiles expose allowed module IDs and declared default module IDs; this milestone does not execute automatic installation.

| P0.2-D | Untyped Workspace fails closed | Disposable Control DB integration |
| P0.2-E | Install and Enable enforce profile allowlist | Service integration |
| P0.2-F | Disable remains available for cleanup | Lifecycle integration |

| P0.2-H | Existing lifecycle RBAC/audit behavior remains intact | Disposable Control DB integration |
| P0.2-I | No persistent DB or business data modified | Command/test scope and Git review |

## Approval Boundary

Source changes, builds, and integration tests that create/drop uniquely named localhost-only disposable databases are in scope. No persistent Control DB migration, Tenant DB change, Workspace reclassification, persistent provisioning, commit, push or deployment is authorized by this brief.
