# P0.6 — Workspace-type Navigation, Default Roles & Permission Catalog

- Date: 2026-11-13
- Status: IMPLEMENTATION COMPLETE — source and verification complete
- Plan revision: 2.7
- Scope: Control Plane source, API, Workspace UI, disposable verification only

## 1. Outcome

Implemented type-aware Workspace permission definitions, role matrices, read-only role listing, cross-type permission/role validation, and server-composed navigation. POS and ONLINE continue to use separate Workspace IDs and Tenant databases. No persistent Control/Tenant database was changed.

## 2. Backend changes

### Typed permission catalog
- Replaced the unqualified catalog with `WORKSPACE_PERMISSION_CATALOG`.
- Each definition carries a stable permission key, description, owner (`core` or `commerce`), supported Workspace Types, and optional module ID.
- Core permissions support POS and ONLINE.
- Commerce permissions are explicitly POS-only and owned by the `commerce` module.
- Preserved all existing permission keys and the compatibility export `WORKSPACE_PERMISSIONS`.

### Type-aware role matrices
- POS: Admin, Manager, Cashier, Inventory Staff (on-demand), Member, Viewer.
- ONLINE: Admin, Manager, Member, Viewer; no Cashier or Inventory Staff.
- Default role seeding resolves the persisted Workspace Type + exact Provisioning Profile ID/version and uses the Profile allow-list. This allows provisioning to seed default-module grants before module installation is finalized.
- Seeding is additive/idempotent; existing customized grants are not overwritten or deleted.
- Platform-admin access remains outside Workspace roles.

### Safe role and permission operations
- Added `workspacePolicy()` as the single persisted Type/Profile resolver for Workspace RBAC/navigation operations. Missing, stale, or mismatched Type/Profile fails closed.
- `GET /workspaces/:workspaceId/roles` is now read-only: it does not seed Permission, Role, or RolePermission rows.
- Role listing filters to role keys valid for the current Workspace Type and only returns permissions available through the persisted Profile and currently enabled Module installations.
- Member add/change rejects role keys not in the target Type's role matrix.
- Permission updates validate the entire set before writes; duplicate, unknown, cross-type, profile-disallowed, disabled-module, and out-of-matrix grants are rejected.
- Admin remains immutable through the role-permission editor. Owner bypass remains Workspace-scoped and does not bypass the P0.5 Module Capability Guard.

### Navigation API
- Added `workspace-navigation-catalog.ts` with stable item IDs, labels, routes, icon identifiers, supported Workspace Types, required permissions, and optional Module ownership.
- Added authenticated `GET /api/workspaces/:workspaceId/navigation`.
- Navigation requires an active membership and derives effective permissions from the membership's role grants (or available Workspace permissions for its Owner).
- Items are filtered by persisted Type/Profile, enabled Module installations, and effective permissions. ONLINE cannot receive POS/Commerce navigation.

## 3. Web changes

- Added reusable `WorkspaceNavigation` component that consumes the authenticated server-composed navigation response.
- POS shell now renders catalog-provided navigation instead of a hardcoded Orders link.
- ONLINE landing renders its own type-compatible navigation.
- Removed POS/Commerce product links from the generic legacy/unclassified Workspace shell; it retains Workspace switching and logout only.
- Added browser coverage for ONLINE absence of POS routes and POS navigation rendering.
