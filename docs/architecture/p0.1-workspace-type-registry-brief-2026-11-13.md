# P0.1 — Workspace Type & Registry

- Track: 0 — Platform Separation Foundation
- Status: DONE — implementation, automated checks and disposable PostgreSQL migration rehearsal passed
- Started: 2026-11-13
- Source of truth: `plan.md`

## Objective

Introduce the first-class `POS` and `ONLINE` Workspace Types in the Control Plane and require an explicit type for every newly created Workspace. Preserve existing Workspace data and do not infer legacy types.

## Inspection Findings

- At inspection time, Control Plane Prisma schema had `WorkspaceStatus`, but no Workspace Type enum or field.
- `Workspace` records already own a separate `WorkspaceDatabase` record.
- `WorkspacesService.create()` currently accepts only slug, name and owner; it provisions a dedicated Tenant DB.
- `GET /workspaces` currently omits Workspace Type.
- Workspace picker currently creates a Workspace without asking for its product type.
- Existing workspaces include `pos-local` and disposable/test workspaces. Their intended product type must not be inferred from slug/name or their current schema.
- The repository has extensive pre-existing uncommitted work. All changes must remain scoped and preserve it.

## Scope

1. Add Control Plane enum `WorkspaceType` with `POS` and `ONLINE`.
2. Add nullable `Workspace.type` and an additive Control DB migration candidate. Nullable is a compatibility bridge for existing rows only; no legacy backfill is included in P0.1.
3. Require `type` on all new Workspace creation requests and reject missing/invalid values before creating records.
4. Return `type` in Workspace list responses.
5. Prevent provisioning a Workspace whose type is missing.
6. Update Workspace picker to select POS or Online explicitly and display the type for existing/new Workspaces.
7. Update disposable test fixtures and bootstrap tests to specify a type explicitly.
8. Add focused verification for valid types, invalid/missing type rejection, and no provisioning when type is absent.
9. Update `plan.md` and this report with evidence and remaining approval gates.

## Out of Scope

- Applying the Control DB migration to any persistent environment.
- Backfilling or reclassifying existing Workspaces, including `pos-local`.
- Creating or deleting a Workspace/Tenant DB in a persistent environment.
- Provisioning Profiles, Module Compatibility, Type-specific RBAC/navigation/API guards (P0.2 onward).
- Moving business data, changing Tenant schemas, or enabling POS/Online synchronization.
- Commit, push, deploy, or production activation.

## Design Decisions

- Type values are exactly `POS` and `ONLINE`.
- Type is immutable through ordinary Workspace update flows; conversion is a separate future migration workflow.
- The DB field remains nullable in this additive milestone so existing rows are preserved without guessed classification. New application-created Workspace rows must always have a valid type.
- Provisioning refuses a null type. Existing ACTIVE Workspaces are not modified by this change.
- The migration remains unapplied to persistent Control DBs. Applying it requires a separate explicit target/environment approval.

## Risks / Open Items

- Existing Workspace type assignments require a separately reviewed inventory and explicit mapping decision. Do not classify `pos-local` or other workspaces automatically.
- Current Control DB migration runner and deployment procedure must be reviewed before any persistent apply.
- Test scripts that create disposable Workspaces must pass a type explicitly.

## Approval Boundary

Local source changes, Prisma schema validation/client generation, and tests against mocks or disposable databases are within this milestone. Applying the migration to a persistent Control DB, changing any existing Workspace, or provisioning a persistent Workspace is not authorized by this brief.
